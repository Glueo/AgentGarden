# OpenViking 清理与写入治理 Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.
> 本文是给其他模型独立审查的建议清单，不是执行授权。上面的执行方式仅供具备该 Skill 且另获授权的 Hermes 使用；其他模型按自身工具能力处理。当前用户只要求规划、理由和建议修改事项，不要求执行、提交代码或修改记忆。

**Goal:** 在保留有效个人记忆、知识资料和历史证据的前提下，降低测试污染、过时状态误召回和重复记忆，并治理未来写入源。

**Architecture:** 先核实实际状态和建立检索基线，再隔离未来测试、统一写入归属，随后对经确认的目标做小批量清理。优先使用官方配置和公开接口，保持 Hermes core 零源码改动；模板定制与大规模迁移仅在有明确收益证据时采用。

**Tech Stack:** Hermes 原生 OpenViking provider、OpenViking 服务及 HTTP/SDK、Agent Garden Python 安装器和同步器、Hermes Skills、Markdown 知识库。

---

## 0. 如何使用这份手册

请接手模型先对每项给出「采纳／调整后采纳／暂缓／拒绝」，补充依据，再形成最小执行范围。不要把本文的推测、候选文件名或历史运行状态当成当前事实。

本文涵盖原建议的全部十项：测试隔离、Memory Policy、测试型执行记忆清理、Trajectory 去重、失效系统知识、Peer 收敛、分类调整、acceptance 资源、Memory Templates、检索验收集。

### 全局边界

- 当前阶段只做审查和方案；实际删除、迁移、配置变更、停服、重启需要另行明确授权。
- 用户倾向功能完整前提下的最小系统；优先修正写入源，避免新增插件、定时清理器或第二套 Skill 管理系统。
- Hermes core 保持零源码改动；不要为绕过现有行为直接修改安装包或核心代码。
- 主模型、fallback、辅助模型和凭据保持用户当前选择，本任务不优化模型路由。
- Skills 的变更走用户明确请求及原生审批流程；本清理任务不自动生成或整顿 Skills。
- `.env`、认证文件和含凭据的配置只在具体授权和必要范围内处理，输出采用字段白名单和脱敏。凭据不进入计划、日志、Git 或聊天。
- 保留仓库中用户已有未提交修改；不自动 commit、push、reset 或恢复文件。
- 批量操作必须有精确目标清单、可回滚备份、逐项结果；文件名模式用于发现候选，不直接驱动删除。
- 文档的建议状态、已批准决策和已完成事实应明确区分，避免本次讨论再次被提取成「已经执行了清理」。

## 1. 基本原理：为什么要清理这些，而不是清空数据库

| 概念 | 用途 | 本次治理重点 |
|---|---|---|
| Hermes 内置记忆 | 每次会话带上的少量常用事实与偏好 | 保持现有最小核心，不将 Viking 全量资料搬回来 |
| Viking Session / archive | 保存会话及提取的来源证据 | 保留可追溯历史；核实实际存在的内容和恢复能力 |
| Viking memories | 从会话提取或显式写入的长期资料 | 清理错误分类、过时活跃说明和低价值测试内容 |
| Viking resources | Wiki、外部文档、图片等资料 | 正式知识与测试资产分离 |
| L0 / L1 / L2 | 摘要、概览、完整内容的分层读取 | 保持摘要、正文和索引一致，而不是删除摘要文件 |
| Memory Policy | 允许提取哪些类型、面向哪些对象 | 控制未来提取范围；不等于删除已有记忆 |
| Memory Templates | 各类型如何判断、组织和合并内容 | 必要时定点纠正提取质量 |
| Agent Evolution | 案例、执行轨迹、经验的积累能力 | 暂缓扩展，先确认实际状态及是否符合需求 |
| User / Peer | 用户公共空间与某助手的独立空间 | 避免同一用户事实无必要分流 |

Viking 主要通过保存和召回资料影响 Hermes 的回答，不是在每次保存记忆时训练主模型参数。治理目标是提高资料质量和检索效果，不是追求文件最少。

## 3. 建议优先级总表

| 优先级 | 建议 | 推荐判断 | 理由 |
|---|---|---|---|
| P0 | 一致性备份、检索基线、停止新增污染 | 必做前提 | 避免边清边长，保证可证明有效、可恢复 |
| P0 | 测试与生产隔离 | 优先采纳 | 从写入源解决明确的污染 |
| P0 | 核实并明确基础提取策略 | 调整后采纳 | 固定意图，但必须识别账号和会话覆盖 |
| P1 | 清理确认无用的测试执行记忆 | 采纳 | 价值低、证据明确，适合首批小范围操作 |
| P1 | 收敛 Hermes 实体中的失效状态 | 优先采纳 | 矛盾的「当前状态」容易直接误导回答 |
| P1 | 统一未来用户事实写入归属 | 采纳 | 单用户场景可减少维护复杂度 |
| P1 | 核对并迁出/清理 acceptance | 逐项采纳 | 检索可见，但可能混有有效材料 |
| P2 | 合并旧 Peer 与用户重复事实 | 分批采纳 | 有收益但需保护事实、日期和来源 |
| P2 | Trajectory 去重和分类修正 | 选择性采纳 | 标题相似和分类重叠都不等于无价值 |
| P3 | 自定义 Memory Templates | 证据驱动、后置 | 会带来维护与升级成本，且与安装器当前行为冲突 |
| 暂缓 | 开启/扩大 Agent Evolution | 暂缓 | 先把输入、基线和提取质量控制好 |

## 4. 具体清理手册

### A. 建立可靠备份和操作清单

**建议修改事项**

- [ ] 确定安全维护窗口，暂停相关写入者并等待在途任务处理到可记录的状态。
- [ ] 采用当前存储后端支持的一致性备份方式；需要停服时另行授权。
- [ ] 备份数据、必要配置和待处理任务状态；敏感备份保存在受保护位置，不放进仓库。
- [ ] 记录备份范围、恢复步骤和校验信息，先在隔离位置验证可恢复性。
- [ ] 为每个拟变更 URI 建立清单：来源、操作、理由、目标 URI、原文备份、内容校验、关联项、回读结果。

**理由**：运行中简单复制数据库和文件目录可能时间点不一致；Session archive 是证据来源，不能代替完整可恢复备份。

**停止条件**：无法确认一致性或恢复路径时，保持只读，不开始破坏性清理。

### B. 先建立检索质量基线

**建议修改事项**

- [ ] 使用第 7 节的固定查询集，保存实际返回的 URI、排序、摘要、分数和耗时。
- [ ] 区分快速检索、深检索和 Hermes 自动注入；至少覆盖日常使用路径。
- [ ] 固定相同的身份、scope、模式、limit 和服务条件，记录每次改动变量。
- [ ] 对动态状态问题同时评价「检索资料是否有历史日期」和「最终回答是否进行实时检查」。

**理由**：文件数量减少不能证明检索变好了。该工作应放在清理前，而不是低优先级收尾。

**注意**：检索验收与对话端到端测试本身也要控制写入，避免新的测试答案被存成生产记忆。

### C. 隔离未来测试数据

**建议修改事项**

- [ ] 只验证聊天模型连通性的测试，在测试进程范围关闭不需要的记忆采集；不影响正常个人会话。
- [ ] 需要验证记忆提取的测试使用隔离用户或测试实例；验证所有读写路径的隔离边界。
- [ ] 需要管理员设置、全局模板或全局索引变更的测试，优先使用独立实例，避免影响同服务生产账号。
- [ ] 同时覆盖会话自动提取、显式记忆写入/镜像、资源上传和测试任务重试入口。
- [ ] 为测试空间设置明确的测试标识和清理边界，结束后按精确清单清理。
- [ ] 禁止测试脚本默认回退到 `gwen`；缺少测试目标时明确失败。

**理由**：只换资源目录或只换 Hermes 会话名称，不一定改变实际 memory user；只清历史内容也不能阻止继续污染。

**验证**：在隔离空间写入唯一测试标识，确认生产身份的日常检索和自动注入不会出现它，并确认后台提取结果同样在隔离空间。不要把标识写入生产空间后再用删除证明隔离。

### D. 明确 Memory Policy 和 Agent Evolution

**建议修改事项**

- [ ] 先读取实际有效值，记录每项来源与覆盖关系。
- [ ] 推荐以个人事实、偏好、对象说明和重要事件为基本范围，即 `profile/preferences/entities/events`。
- [ ] 对 `identity/soul` 单独判断用途：如果只是重复 Hermes 人格与系统提示，可以暂缓；如承担明确的独立功能则保留。
- [ ] 当前阶段建议暂停新增 `cases/trajectories/experiences`，但保留其中已有独立价值的内容待评估。
- [ ] 核实 `tools/skills` 等类型是否启用、是否有新写入；出现旧 `patterns` 目录时按实际版本与来源审查，不假设仍是默认类型。
- [ ] 使用当前版本支持的 policy/schema，不复制未经校验的布尔键或类型名。
- [ ] 明确账号开关与服务默认值的关系；本机代码中的默认字段是 `server.agent_evolution.enabled`。
- [ ] 改动后读取账号有效状态，并在隔离空间验证一次真实提取结果，而非只看配置文件。

**理由**：提取白名单、Evolution 和已有索引是不同层。关闭新提取不会删除旧资料，也不会自动阻止旧资料被搜索。

**需接手模型判断**：是否需要改变 working memory；本计划没有证据支持顺带关闭它。基础类型也不是全部无条件开启越多越好。

### E. 停止未来 Peer 分流，保留历史可检索性

**建议修改事项**

- [ ] 确认当前是否确有多助手独立记忆需求；如有，则只统一用户事实，不取消必要的助手独立空间。
- [ ] 单用户、单助手场景推荐使用 `viking://user/gwen/memories/` 作为未来用户事实归属。
- [ ] 从环境标识、链接客户端配置和 Hermes YAML 各来源一起检查旧 Peer 设置；不能只把低优先级字段设为空就认为关闭。
- [ ] 修改 Garden 安装器的身份写入逻辑，避免下次安装重新注入 `OPENVIKING_AGENT=hermes`。
- [ ] 检查 Garden 同步器及其删除/回读客户端使用的身份是否一致；资源写入路径和访问范围应明确验证。
- [ ] 新建 Hermes 会话验证未来写入归属；旧会话可能继续持有先前捕获的客户端身份，需记录过渡期。
- [ ] 验证无 Peer 时能按官方行为检索旧 Peer 内容，并评价召回范围变宽后的相关性。

**理由**：官方支持无 Peer，旧 Peer 内容无需先全量搬迁；先修未来写入源可减少继续产生重复。取消 Peer 也可能扩大搜索范围，所以仍需回归。

**关键修正**：不强制「先合并所有旧内容，再取消 Peer」；更稳妥的是备份后统一未来写入，再逐批治理旧内容。

### F. 删除确认低价值的测试记忆

**候选模式，仅用于发现**

- `acceptance_probe_*`
- `exact_probe_*`、`exact_reply_*`、`exact_static_*`、`exact_required_string_*`
- `MAIN_OK*`、`baseline_confirmation_response_*`
- 仅描述「成功回复指定字符串」的 Case / Trajectory / Experience
- 一次性可用性探针，且没有独立诊断价值的结果

**建议修改事项**

- [ ] 读取每个候选的完整正文，区分「无意义成功记录」与「仍可复用的故障诊断结论」。
- [ ] 查验关联 Case、Trajectory、Experience 和来源 archive，避免留下一批指向已删对象的链接。
- [ ] 对确定无用的记录使用当前版本支持的公开删除接口；本工具 `viking_forget` 仅支持明确授权的单个精确记忆文件 URI，不能据此泛化为资源目录删除。
- [ ] 等待异步任务终态，回读确认目标不存在，并核验搜索及相关摘要不再保留该条目的实质内容。

**理由**：这类内容价值低，适合首批清理，但不能用正则匹配代替内容审查。

## 9. 风险、回滚和暂停条件

- **误合并**：个人事实有冲突且证据不足时，保持原文并标记待判断。
- **并发写入**：旧会话或重放任务继续写入时，先厘清来源，再决定暂停、切换或重新开会话。
- **重新污染**：同步器、测试默认值、安装器恢复旧设置时，停止继续删文件，修复源头。
- **索引不一致**：正文已改但摘要或搜索仍旧时，检查公开刷新与异步任务状态；不要立即全库重建。
- **访问范围变化**：取消 Peer 后旧内容更多地进入召回时，先核查 scope 与排名，不通过盲删解决。
- **权限受阻**：管理 API 403 或缺少受支持的操作能力时，报告阻塞并申请正确权限；不绕过保护。
- **原文不全**：长文件截断、分页未完成或来源缺失时，停止覆盖和删除。
- **回滚需求**：恢复数据及与之匹配的索引/配置状态，不能只恢复几份 Markdown 就声称恢复完整。
