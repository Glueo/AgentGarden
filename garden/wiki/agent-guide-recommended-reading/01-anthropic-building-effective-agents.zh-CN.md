# 构建高效的 Agent

发布于 2024 年 12 月 19 日

我们曾与各行各业数十个构建 LLM Agent 的团队合作。实践一再表明，最成功的实现采用的是简单、可组合的模式，而不是复杂的框架。

*注：自 2024 年 12 月以来，本文所述的工具生态已经发生了很大变化。关于我们目前采用的方法，请参阅 [**我们如何构建 Claude Managed Agents**](https://www.anthropic.com/engineering/managed-agents) *以及 [**Managed Agents 文档**](https://platform.claude.com/docs/en/managed-agents/overview)。*

在过去一年中，我们曾与各行各业数十个构建大语言模型（LLM）Agent 的团队合作。实践一再表明，最成功的实现并未使用复杂的框架或专用库，而是采用了简单、可组合的模式。

本文将分享我们与客户合作以及亲自构建 Agent 的经验，并为开发者提供构建高效 Agent 的实用建议。

## 什么是 Agent？

“Agent”可以有多种定义。一些客户将 Agent 定义为能够长期独立运行、使用各种工具完成复杂任务的完全自主系统。另一些客户则用这个术语描述遵循预定义工作流、规范性更强的实现。在 Anthropic，我们将所有这些变体统称为 **Agent 系统（agentic systems）**，但在架构上明确区分 **工作流（workflows）** 与 **Agent**：

* **工作流**是由预定义代码路径编排 LLM 和工具的系统。
* **Agent** 则是由 LLM 动态主导自身流程和工具使用方式，并自主决定如何完成任务的系统。

下文将详细探讨这两类 Agent 系统。在附录 1（“Agent 的实际应用”）中，我们会介绍客户发现此类系统特别有价值的两个领域。

## 何时使用（以及何时不使用）Agent

构建 LLM 应用时，我们建议尽可能寻找最简单的解决方案，只在确有需要时才增加复杂度。这可能意味着根本不构建 Agent 系统。Agent 系统通常以延迟和成本为代价来换取更好的任务表现，因此你应当判断这种权衡何时才有意义。

当确实需要更高复杂度时，对于定义明确的任务，工作流能够提供可预测性和一致性；而在需要大规模实现灵活性和模型驱动的决策时，Agent 是更好的选择。不过，对许多应用而言，通过检索和上下文示例来优化单次 LLM 调用通常就已足够。

## 何时以及如何使用框架

有许多框架可以简化 Agent 系统的实现，包括：

* [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
* [AWS 的 Strands Agents SDK](https://strandsagents.com/latest/)；
* [Rivet](https://rivet.ironcladapp.com/)：一款通过拖放式 GUI 构建 LLM 工作流的工具；以及
* [Vellum](https://www.vellum.ai/)：另一款用于构建和测试复杂工作流的 GUI 工具。

这些框架简化了调用 LLM、定义和解析工具、串联调用等标准底层任务，使开发者可以轻松上手。但它们往往会引入额外的抽象层，遮蔽底层的提示词和响应，从而增加调试难度。当更简单的方案已经足够时，它们也可能诱使开发者加入不必要的复杂性。

我们建议开发者从直接使用 LLM API 开始：许多模式只需几行代码即可实现。如果确实使用框架，请确保理解其底层代码。对内部实现作出错误假设，是客户常见的出错原因。

有关一些实现示例，请参阅我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 构建模块、工作流与 Agent

本节将探讨我们在生产环境中见到的 Agent 系统常见模式。我们从基础构建模块——增强型 LLM——讲起，再逐步提高复杂度，从简单的组合式工作流一直讲到自主 Agent。

### 构建模块：增强型 LLM

Agent 系统的基本构建模块，是通过检索、工具和记忆等能力得到增强的 LLM。我们当前的模型能够主动使用这些能力——自行生成搜索查询、选择适当的工具，并判断应保留哪些信息。

我们建议实现时重点关注两个方面：根据具体用例定制这些能力，并确保为 LLM 提供易用且文档完善的接口。实现这些增强能力的方法有很多，其中一种是使用我们最近发布的 [模型上下文协议（Model Context Protocol，MCP）](https://www.anthropic.com/news/model-context-protocol)。开发者只需实现一个简单的[客户端](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)，即可接入不断扩大的第三方工具生态。

在本文余下部分，我们假定每次 LLM 调用都可以使用这些增强能力。

### 工作流：提示链

提示链将任务分解为一系列步骤，每次 LLM 调用都会处理上一次调用的输出。你可以在任何中间步骤加入程序化检查（见下图中的“闸门”），确保流程仍在正确轨道上。

**何时使用此工作流：** 当任务可以轻松、清晰地分解为固定子任务时，这种工作流最为理想。其主要目标是用延迟换取更高的准确性：让每次 LLM 调用处理更容易的任务。

**适合使用提示链的示例：**

* 生成营销文案，然后将其翻译为另一种语言。
* 撰写文档大纲，检查大纲是否符合特定标准，再根据大纲撰写文档。

### 工作流：路由

路由会对输入进行分类，并将其引导至专门的后续任务。该工作流可以实现关注点分离，并构建更有针对性的提示词。如果不采用这种工作流，针对某一类输入所做的优化可能会损害其他类型输入的表现。

**何时使用此工作流：** 对于包含不同类别、适合分别处理的复杂任务，如果 LLM 或较传统的分类模型／算法能够准确完成分类，路由就很有效。

**适合使用路由的示例：**

* 将不同类型的客户服务咨询（一般问题、退款请求、技术支持）引导至不同的下游流程、提示词和工具。
* 为获得最佳综合表现，将简单／常见问题路由至 Claude Haiku 4.5 等更小且更具成本效益的模型，将困难／少见问题路由至 Claude Sonnet 4.5 等能力更强的模型。

### 工作流：并行化

有时，可以让多个 LLM 同时处理一项任务，再通过程序汇总其输出。这种并行化工作流主要有两种形式：

* **分区（Sectioning）**：将任务拆分为彼此独立、可并行运行的子任务。
* **投票（Voting）**：多次运行同一任务，以获得多样化的输出。

**何时使用此工作流：** 如果拆分后的子任务可以通过并行执行来提速，或者需要多个视角或多次尝试才能获得置信度更高的结果，并行化就很有效。对于涉及多项考量的复杂任务，如果通过单独的 LLM 调用分别处理每一项考量，使其专注于特定方面，LLM 通常会表现得更好。

**适合使用并行化的示例：**

* **分区：**
  + 实施安全护栏：一个模型实例处理用户查询，另一个实例检查查询中是否包含不当内容或请求。相比让同一次 LLM 调用同时处理安全护栏和核心响应，这种方式往往表现更好。
  + 自动进行 LLM 性能评估，其中每次 LLM 调用针对给定提示词评估模型表现的不同方面。
* **投票：**
  + 审查一段代码是否存在漏洞，使用多个不同的提示词进行审查，并在发现问题时标记代码。
  + 评估给定内容是否不当，让多个提示词评估不同方面，或设置不同的投票阈值，以平衡误报与漏报。

### 工作流：编排器—工作节点

在编排器—工作节点（orchestrator-workers）工作流中，一个中央 LLM 会动态分解任务，将任务委派给作为工作节点的 LLM，并综合它们的结果。

**何时使用此工作流：** 这种工作流非常适合无法预先判断需要哪些子任务的复杂任务（例如，在编码任务中，需要修改的文件数量以及各文件中的修改性质，很可能取决于具体任务）。尽管它在结构上与并行化相似，但关键区别在于灵活性：子任务并非预先定义，而是由编排器根据具体输入来决定。

**适合使用编排器—工作节点的示例：**

* 每次都需要对多个文件进行复杂修改的编码产品。
* 需要从多个来源收集并分析潜在相关信息的搜索任务。

### 工作流：评估器—优化器

在评估器—优化器（evaluator-optimizer）工作流中，一次 LLM 调用生成响应，另一次调用则在循环中进行评估并提供反馈。

**何时使用此工作流：** 当评估标准清晰，且迭代改进能带来可衡量的价值时，这种工作流尤其有效。是否适用主要有两个判断信号：第一，当人类清楚表达反馈时，LLM 的响应确实可以得到改进；第二，LLM 自身也能够提供这类反馈。这类似于人类作者为了产出精雕细琢的文档而经历的迭代写作过程。

**适合使用评估器—优化器的示例：**

* 文学翻译：负责翻译的 LLM 起初可能无法捕捉某些微妙之处，但负责评估的 LLM 可以给出有用的批评意见。
* 复杂的搜索任务：需要经过多轮搜索和分析才能收集全面的信息，并由评估器判断是否有必要继续搜索。

### Agent

随着 LLM 在理解复杂输入、推理与规划、可靠使用工具以及从错误中恢复等关键能力上日趋成熟，Agent 正逐渐进入生产环境。Agent 从人类用户发出的命令或与用户的交互式讨论开始工作。任务明确后，Agent 会独立规划并执行，并可能返回询问人类以获取更多信息或判断。在执行过程中，Agent 必须在每一步都从环境中获得“真实依据”（例如工具调用结果或代码执行结果），以评估自身进度。随后，Agent 可以在检查点或遇到阻碍时暂停，等待人类反馈。任务通常在完成时终止，但为了保持控制，也常会加入停止条件（例如最大迭代次数）。

Agent 可以处理复杂任务，但实现方式往往很直截了当。它们通常只是根据环境反馈，在循环中使用工具的 LLM。因此，清晰、周全地设计工具集及其文档至关重要。我们会在附录 2（“对工具进行提示工程”）中进一步介绍工具开发的最佳实践。

**何时使用 Agent：** Agent 适用于难以或无法预判所需步骤数量、也无法硬编码固定路径的开放式问题。LLM 可能会运行许多个回合，因此你必须对其决策能力抱有一定程度的信任。Agent 的自主性使其非常适合在可信环境中规模化执行任务。

Agent 的自主性质意味着更高的成本，也存在错误不断累积的可能。我们建议在沙箱环境中进行充分测试，并设置适当的安全护栏。

**适合使用 Agent 的示例：**

以下示例来自我们自己的实现：

* 用一个编码 Agent 解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet)，这类任务需要根据任务描述编辑许多文件；
* 我们的 [“计算机使用”参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，其中 Claude 会使用计算机完成任务。

## 组合与定制这些模式

这些构建模块并不是强制规范，而是开发者可以根据不同用例加以调整和组合的常见模式。与所有 LLM 功能一样，成功的关键在于衡量性能并迭代实现。再次强调：只有在能够明确改善结果时，才应考虑增加复杂度。

## 总结

在 LLM 领域，成功并不取决于构建最复杂精巧的系统，而在于构建真正适合自身需求的系统。从简单的提示词开始，通过全面评估对其进行优化；只有在简单方案力有不逮时，才加入多步骤 Agent 系统。

实现 Agent 时，我们力求遵循三项核心原则：

1. 让 Agent 的设计保持 **简单**。
2. 明确展示 Agent 的规划步骤，优先保证 **透明度**。
3. 通过全面的工具 **文档和测试**，精心打造 Agent—计算机接口（ACI）。

框架可以帮助你快速上手，但在走向生产环境的过程中，不要犹豫，应酌情减少抽象层并使用基础组件进行构建。遵循这些原则，你就能创建出不仅强大，而且可靠、可维护并能赢得用户信任的 Agent。

## 附录 1：Agent 的实际应用

我们与客户的合作揭示了 AI Agent 特别有前景的两类应用，体现了上述模式的实际价值。这两类应用都表明：对于既需要对话又需要行动、成功标准清晰、能够形成反馈循环且可以纳入有意义的人类监督的任务，Agent 最能发挥价值。

### A. 客户支持

客户支持通过工具集成，将人们熟悉的聊天机器人界面与增强能力结合起来。它天然适合更加开放式的 Agent，原因如下：

* 支持交互天然遵循对话流程，同时又需要访问外部信息并执行操作；
* 可以集成工具来获取客户数据、订单历史和知识库文章；
* 发放退款或更新工单等操作可以通过程序完成；以及
* 可以通过用户定义的问题解决标准，清晰地衡量是否成功。

已有多家公司通过按使用效果定价的模式证明了这种方法的可行性：只有成功解决问题才收费，体现了它们对自身 Agent 有效性的信心。

### B. 编码 Agent

软件开发领域已经展现出 LLM 功能的巨大潜力，其能力正从代码补全逐步发展到自主解决问题。Agent 在这个领域尤其有效，原因如下：

* 代码解决方案可通过自动化测试进行验证；
* Agent 可以将测试结果作为反馈，反复迭代解决方案；
* 问题空间定义明确且结构清晰；以及
* 输出质量可以客观衡量。

在我们自己的实现中，如今 Agent 只根据拉取请求（pull request）的描述，就能解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准中的真实 GitHub issue。不过，尽管自动化测试有助于验证功能，人类审查对于确保解决方案符合更广泛的系统要求仍然至关重要。

## 附录 2：对工具进行提示工程

无论构建哪一种 Agent 系统，工具都很可能是 Agent 的重要组成部分。通过在我们的 API 中精确指定结构和定义，[工具](https://www.anthropic.com/news/tool-use-ga)可以让 Claude 与外部服务和 API 进行交互。如果 Claude 打算调用工具，它的 API 响应中会包含一个[工具使用块（tool use block）](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具定义和规范应当像整体提示词一样，得到同等程度的提示工程投入。在这篇简短的附录中，我们将介绍如何对工具进行提示工程。

同一个操作通常有多种指定方式。例如，可以通过编写 diff 来指定文件修改，也可以重写整个文件。对于结构化输出，可以将代码放在 Markdown 中返回，也可以放在 JSON 中返回。在软件工程中，此类差异只是表现形式不同，可以在彼此之间进行无损转换。但对 LLM 而言，有些格式比其他格式难写得多。编写 diff 时，需要在写出新代码之前，就知道代码块头部所标示的变更行数。在 JSON 而不是 Markdown 中编写代码，则需要对换行符和引号进行额外转义。

关于如何决定工具格式，我们有以下建议：

* 给模型足够的 token 用来“思考”，避免它写到一半陷入困境。
* 采用与模型在互联网自然文本中常见格式相近的格式。
* 确保不存在格式上的额外负担，例如必须精确统计数千行代码，或对所写的任何代码进行字符串转义。

一条经验法则是：想一想人们在设计人机接口（HCI）上投入了多少精力，并计划投入同样多的精力来创建出色的 *Agent—计算机接口*（ACI）。以下是一些具体建议：

* 设身处地从模型的角度思考。只根据说明和参数，是否一眼就能明白如何使用这个工具，还是必须仔细琢磨？如果是后者，模型很可能也会面临同样的问题。优秀的工具定义通常包括使用示例、边界情况、输入格式要求，以及与其他工具之间清晰的职责边界。
* 如何修改参数名称或说明，才能让含义更直观？可以把这件事想象成给团队中的初级开发者编写一份出色的文档字符串（docstring）。使用许多相似工具时，这一点尤其重要。
* 测试模型如何使用工具：在我们的 [Workbench](https://console.anthropic.com/workbench) 中运行大量示例输入，观察模型会犯哪些错误，并据此迭代。
* 对工具进行[防错设计（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)。调整参数，让错误更难发生。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建 Agent 时，我们优化工具所花的时间实际上比优化整体提示词还要多。例如，我们发现，当 Agent 离开根目录后，模型在使用采用相对文件路径的工具时会出错。为解决这个问题，我们修改了工具，使其始终要求使用绝对文件路径——随后发现，模型能够毫无差错地使用这种方式。
